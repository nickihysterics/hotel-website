# Развёртывание и эксплуатация

## Локальный стенд

### Требования

- Docker Engine или Docker Desktop;
- Docker Compose v2;
- свободные порты 80, 443 и 8081 либо альтернативы в `.env`.

### Запуск

```bash
cp .env.example .env
docker compose up -d --build
docker compose ps
```

MySQL применяет `database/init.sql` только при первом создании volume `db-data`.
Повторный запуск контейнеров сохраняет данные.

### Проверка

```bash
curl -kI https://localhost/
BASE_URL=https://localhost ./scripts/smoke.sh
docker compose logs --tail=100 web nginx db
```

## Порты

| Сервис | Внутренний порт | Переменная внешнего порта |
| --- | --- | --- |
| Nginx HTTP | 80 | `HOTEL_HTTP_PORT` |
| Nginx HTTPS | 443 | `HOTEL_HTTPS_PORT` |
| phpMyAdmin | 80 | `HOTEL_PMA_PORT` |
| MySQL | 3306 | наружу не публикуется |

## Обновление локальной установки

```bash
git pull --ff-only
docker compose build --pull web nginx
docker compose run --rm --no-deps web composer install --no-dev --classmap-authoritative
docker compose up -d
```

Если изменена схема, сначала примените профильную миграцию. `docker compose down -v`
удаляет всю локальную базу и допустим только для заведомо демонстрационных данных.

## Резервное копирование

Пример логического backup локальной базы:

```bash
docker compose exec -T db sh -c \
  'mysqldump -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" --single-transaction "$MYSQL_DATABASE"' \
  > hotel-backup.sql
```

Файл дампа может содержать персональные данные и не должен попадать в Git. Для
production требуется шифрование, отдельное хранилище, контроль срока хранения и
регулярная проверка восстановления.

## Восстановление на отдельном стенде

1. Поднять чистую MySQL нужной версии.
2. Создать пустую базу и пользователя.
3. Импортировать проверенный дамп.
4. Применить отсутствующие миграции.
5. Запустить приложение с отдельным `.env`.
6. Выполнить smoke и ручной приёмочный сценарий.

Не проверяйте восстановление поверх единственной рабочей базы.

## Production-чек-лист

Текущий Compose — локальный и production-подобный стенд, но не готовая инфраструктура.
Перед вводом в эксплуатацию необходимо:

- вынести секреты из файловой поставки в защищённое хранилище;
- заменить локальный сертификат доверенным TLS;
- не публиковать phpMyAdmin либо закрыть его VPN и отдельной авторизацией;
- изменить все demo-пароли и удалить демонстрационные аккаунты;
- подключить реальный эквайринг, webhook и идемпотентность;
- подключить SMTP/SMS и перестать показывать reset-ссылку в интерфейсе;
- настроить миграции без повторного baseline-init;
- добавить health endpoint, централизованные логи, error tracking и алерты;
- настроить автоматический зашифрованный backup и restore drill;
- определить retention персональных данных и процедуру удаления;
- ограничить ресурсы контейнеров и обновлять базовые образы;
- выполнить нагрузочное и security-тестирование;
- задокументировать SLA, владельцев и порядок отката.

## Откат

Откат кода выполняется на предыдущий проверенный commit без отката базы «назад».
Изменения схемы должны проектироваться как совместимые или сопровождаться отдельно
проверенным restore-планом. Перед каждым production-обновлением обязателен backup.
