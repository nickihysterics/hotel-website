# Разработка

## Рабочее окружение

Для воспроизводимой разработки используется Docker Compose. Локальная установка PHP, Composer, MySQL и Nginx не требуется.

```bash
cp .env.example .env
docker compose up -d --build
docker compose run --rm --no-deps web composer install
```

## Проверки

Перед коммитом запустите:

```bash
docker compose run --rm --no-deps web composer check
docker compose config --quiet
```

`composer check` последовательно выполняет:

1. синтаксическую проверку PHP-файлов;
2. PHPStan уровня 6;
3. PHP-CS-Fixer в режиме проверки без записи.

Автоматическое форматирование:

```bash
docker compose run --rm --no-deps web composer cs:fix
```

## Ветки

Основная ветка `main` должна оставаться готовой к запуску. Для изменений создавайте короткие тематические ветки:

```text
feat/public-booking-form
fix/booking-overlap
docs/local-setup
refactor/admin-resources
```

Не объединяйте в одной ветке несвязанные изменения.

## Коммиты

Сообщения оформляются по Conventional Commits и пишутся в повелительной форме:

```text
feat: добавить публичную форму бронирования
fix: исключить отменённые брони из загрузки
docs: описать локальный запуск
refactor: вынести запросы аналитики в сервис
test: покрыть расчёт доступности
build: обновить образ PHP
ci: добавить статический анализ
chore: обновить служебные файлы
```

Заголовок должен описывать один законченный результат. Причины и ограничения нетривиального решения указываются в теле коммита.

## Pull request

Перед открытием pull request:

- синхронизируйте ветку с актуальным `main` без merge-коммитов, если это безопасно;
- убедитесь, что рабочее дерево не содержит секретов, `.env`, дампов и локальных данных;
- выполните полный набор проверок;
- опишите пользовательский результат и способ проверки;
- приложите скриншоты для изменений интерфейса;
- явно перечислите изменения схемы данных и шаги миграции.

Не переписывайте историю общей ветки и не выполняйте force-push в `main`.

## Стиль PHP

- для новых PHP-файлов обязателен `declare(strict_types=1);`;
- код следует PSR-12 и правилам `.php-cs-fixer.php`;
- SQL-значения передаются параметрами подготовленных запросов;
- динамические идентификаторы таблиц и столбцов допускаются только из закрытого allowlist;
- вывод пользовательских данных экранируется функцией `e()`;
- все изменяющие POST-формы защищаются CSRF-токеном;
- операции, зависящие от текущей доступности, выполняются в транзакции.

## Изменения базы данных

Источник схемы для новой установки — `database/init.sql`. При изменении структуры:

1. обновите полную схему;
2. опишите безопасный путь обновления существующей базы;
3. проверьте внешние ключи, индексы и ограничения;
4. не удаляйте пользовательские данные автоматически без явного решения.

Полный локальный сброс допустим только для демонстрационных данных:

```bash
docker compose down -v
docker compose up -d --build
```

Команда удаляет Docker volume базы и не подходит для среды с ценными данными.
